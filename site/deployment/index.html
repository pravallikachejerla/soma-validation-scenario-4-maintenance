Original Defect Reproduction Steps

Defect: Some customers receive the same discount twice when a promotion qualifies through both an SKU-specific path and a wildcard channel path.

Reproduction Steps

  1. Start the API server: go run ./cmd/api
  2. Seed synthetic data: curl -X POST http://localhost:8080/api/v1/admin/seed
  3. Create a promotion with both SKU-specific and wildcard rule rows for the same promotion ID: 
    curl -X POST http://localhost:8080/api/v1/promotions \
  -H "Content-Type: application/json" \
  -d '{
    "id": "promo-overlap",
    "tenant_id": "tenant-a",
    "name": "Overlap Test",
    "type": "percent",
    "value": 10.0,
    "channel": "web",
    "sku": "SKU-00001",
    "priority": 5,
    "valid_from": "2026-01-01T00:00:00Z",
    "valid_until": "2027-01-01T00:00:00Z"
  }'
  4. Request a price quote for the same SKU and channel: 
    curl -X POST http://localhost:8080/api/v1/pricing/quote \
  -H "Content-Type: application/json" \
  -d '{
    "tenant_id": "tenant-a",
    "customer_id": "cust-001",
    "sku": "SKU-00001",
    "quantity": 1,
    "channel": "web",
    "at": "2026-06-01T00:00:00Z"
  }'
  5. Expected (correct): The promotion is applied once, resulting in a 10% discount.
  6. Actual (defect): The promotion is applied twice (once via SKU-specific path, once via wildcard path), resulting in a 20% discount.

Test Coverage

The defect is covered by tests/public/defect_reproduction_test.go, which asserts that the promotion is applied exactly once and the final price reflects a single 10% discount.

Corrected-Behaviour Verification Steps

Fix: The promotion resolver (internal/promotion/resolver.go) now de-duplicates promotions by ID before applying, ensuring each promotion is applied at most once even when the storage layer returns it via both SKU-specific and wildcard paths.

Verification Steps

  1. Run the defect reproduction test: 
    go test ./tests/public/ -run TestDefectReproduction -v
  2. Expected output: --- PASS: TestDefectReproduction
  3. Run the full public test suite: 
    go test ./tests/public/ -v
  4. Expected output: All 43 tests pass, including:
    • TestDefectReproduction — exact overlap scenario
    • TestDuplicateDiscount — SKU/wildcard overlap
    • TestBatchPricing — batch path parity
    • TestInteractivePricing — interactive path
    • TestWildcardOnlyMatching — wildcard-only promotions
    • TestRepeatedPathMatching — repeated-path matching
  5. Manually verify via API: 
    curl -X POST http://localhost:8080/api/v1/pricing/quote \
  -H "Content-Type: application/json" \
  -d '{"tenant_id":"tenant-a","customer_id":"cust-001","sku":"SKU-00001","quantity":1,"channel":"web","at":"2026-06-01T00:00:00Z"}'
  6. Expected response: applied_promotion_ids contains ["promo-overlap"] exactly once, and final_yen reflects a single 10% discount.

Manual-Override Feature Verification Steps

Feature: Manual price-override approval workflow with per-tenant configurable threshold, two-approval rule above threshold, requester self-approval prevention, mandatory reasons, and complete audit trail.

Verification Steps

  1. Enable the override feature for a tenant: 
    curl -X PATCH http://localhost:8080/api/v1/tenants/tenant-a \
  -H "Content-Type: application/json" \
  -d '{"override_enabled": true, "override_threshold_yen": 5000000}'
  2. Create an override request below threshold (single approval required): 
    curl -X POST http://localhost:8080/api/v1/overrides \
  -H "Content-Type: application/json" \
  -d '{
    "tenant_id": "tenant-a",
    "requester_id": "user-requester",
    "sku": "SKU-00001",
    "channel": "web",
    "customer_id": "cust-001",
    "original_yen": 1000000,
    "override_yen": 800000,
    "reason": "Volume discount for VIP customer"
  }'
  3. Approve the request (single approval sufficient below threshold): 
    curl -X POST http://localhost:8080/api/v1/overrides/{id}/approve \
  -H "Content-Type: application/json" \
  -d '{"approver_id": "user-approver-1", "reason": "Approved per VIP policy"}'
  4. Create an override request above threshold (two approvals required): 
    curl -X POST http://localhost:8080/api/v1/overrides \
  -H "Content-Type: application/json" \
  -d '{
    "tenant_id": "tenant-a",
    "requester_id": "user-requester",
    "sku": "SKU-00001",
    "channel": "web",
    "customer_id": "cust-001",
    "original_yen": 6000000,
    "override_yen": 5500000,
    "reason": "Strategic account discount"
  }'
  5. Attempt self-approval (should fail): 
    curl -X POST http://localhost:8080/api/v1/overrides/{id}/approve \
  -H "Content-Type: application/json" \
  -d '{"approver_id": "user-requester", "reason": "Self-approval attempt"}'
    Expected: HTTP 400 with error "requester cannot approve their own request"
  6. Approve with first approver (status remains pending): 
    curl -X POST http://localhost:8080/api/v1/overrides/{id}/approve \
  -H "Content-Type: application/json" \
  -d '{"approver_id": "user-approver-1", "reason": "First approval"}'
  7. Approve with second approver (status transitions to approved): 
    curl -X POST http://localhost:8080/api/v1/overrides/{id}/approve \
  -H "Content-Type: application/json" \
  -d '{"approver_id": "user-approver-2", "reason": "Second approval"}'
  8. Apply the approved override: 
    curl -X POST http://localhost:8080/api/v1/overrides/{id}/apply
  9. Verify audit trail: 
    curl http://localhost:8080/api/v1/audit?tenant_id=tenant-a&limit=20
    Expected: Audit events for override.requested, override.approved (x2), and override.applied.

Migration & Rollback Instructions

Forward Migration

The migration is backward compatible and additive:

  1. New columns added to tenants table:
    • override_threshold_yen BIGINT NOT NULL DEFAULT 0
    • override_enabled BOOLEAN NOT NULL DEFAULT FALSE
  2. New table override_requests created with index on (tenant_id, created_at DESC).
  3. Existing tenants default to override_enabled = FALSE, preserving legacy behaviour.
  4. Existing tenants default to override_threshold_yen = 0, which means the system default (JPY 5,000,000) applies when the feature is enabled.

Migration Command

go run ./cmd/migrate up

Rollback Instructions

To rollback the override workflow:

  1. Disable the feature for all tenants: 
    UPDATE tenants SET override_enabled = FALSE;
  2. Run the reverse migration: 
    go run ./cmd/migrate down
  3. The reverse migration drops override_requests first, then removes the new columns from tenants.
  4. Existing pricing data and audit logs are preserved.

Rollback Command

go run ./cmd/migrate down

Data Safety

  • No data loss: The migration only adds columns and a new table. No existing data is modified.
  • No API breakage: The public pricing API (/pricing/quote, /pricing/batch) is unchanged.
  • Feature flag: Existing tenants continue to behave identically until override_enabled is set to TRUE.

Known Limitations

1. In-Memory Storage Default

The default storage backend is in-memory (internal/storage/memory.go). Data is lost on server restart. For production deployment, configure PostgreSQL via environment variables.

2. No Authentication

The API does not enforce authentication. The requester_id and approver_id fields are trusted as-is. In production, add an authentication layer (e.g., JWT, OAuth) before the HTTP handlers.

3. No Rate Limiting

The API does not enforce rate limits. In production, add rate limiting middleware to prevent abuse.

4. Single-Node Deployment

The in-process result cache (internal/pricing/aggregator.go) is per-node. Multi-node deployments will have cache misses across nodes.

5. Override Workflow is Additive

The override workflow does not modify the pricing engine. Approved overrides are recorded as audit events but do not automatically adjust future pricing decisions. The apply endpoint marks the override as applied but does not inject a synthetic promotion into the pricing path.

6. No Notification System

Approvers are not notified when a request is created. In production, integrate with email/Slack to notify approvers.

7. No Expiry on Override Requests

Pending override requests do not expire automatically. In production, add a TTL and auto-rejection after expiry.

8. Test Coverage

Public tests cover 43 scenarios. Private tests (reserved by the project) were not run in this deployment. End-to-end Playwright tests are present but require a running server to execute.
