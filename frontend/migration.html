Migration and rollback instructions

Forward migration

The migration is embedded in migrations/0001_init.sql and is idempotent (CREATE TABLE IF NOT EXISTS, ADD COLUMN IF NOT EXISTS), so it is safe to re-run.

  1. Back up the database before migrating.
  2. Apply the migration: 
    go run ./cmd/migrate
  3. Seed the reference data (only needed for a fresh environment): 
    go run ./cmd/seed
  4. Restart the API and verify: 
    curl http://localhost:8080/healthz
curl http://localhost:8080/api/v1/tenants/tenant-a
  5. Confirm every existing tenant reports override_enabled = false and override_threshold_yen = 0. This is what makes the migration backward compatible: existing tenant behaviour is unchanged until the feature is explicitly enabled per tenant.

Enabling the feature for a tenant

curl -X PATCH http://localhost:8080/api/v1/tenants/tenant-a \
  -H "Content-Type: application/json" \
  -d '{"override_enabled": true, "override_threshold_yen": 3000000}'

The tenant's configured threshold supersedes the system default of JPY 5,000,000. Setting override_threshold_yen to 0 restores the default.

Rollback

The feature can be disabled per tenant without a schema change — this is the preferred rollback because it is immediate and loses no data.

  1. Disable the feature for the affected tenant: 
    curl -X PATCH http://localhost:8080/api/v1/tenants/tenant-a \
  -H "Content-Type: application/json" \
  -d '{"override_enabled": false}'
  2. Existing pricing behaviour is restored immediately: the public pricing API never consulted the override workflow, so no pricing result changes.
  3. Full schema rollback (only if the override tables must be removed entirely): 
    go run ./cmd/migrate --down
    or, manually: 
    DROP TABLE IF EXISTS override_requests;
ALTER TABLE tenants
  DROP COLUMN IF EXISTS override_enabled,
  DROP COLUMN IF EXISTS override_threshold_yen;
  4. Audit events for override actions are retained after rollback — the audit trail is append-only by design.

Backward-compatibility guarantees

  • The public pricing API (POST /api/v1/pricing/quote, POST /api/v1/pricing/batch) is unchanged — same request body, same response body, same status codes.
  • The duplicate-discount correction is a pure logic change inside the promotion resolver; no schema, no API, and no configuration change.
  • New tenants default to override_enabled = false and override_threshold_yen = 0 (meaning: use the JPY 5,000,000 system default).
  • No existing column was retyped, renamed, or dropped.
